# 游戏详情页调研规范（子智能体必读）

你要为工作清单里的**每一款**游戏产出一份详情档案。产出会被写进站点详情页，
面向的是**做小游戏复刻决策的产品/技术团队**——他们要判断「这款值不值得抄、
抄的话要花多少成本、怎么改才不算抄」，以及**「不管抄不抄，它能和我们自己的
业务怎么结合」**（见第六节）。

## 一、输入

输入是一个 JSON 文件（形如 `data/detail/_staging/_batch_1_input.json`）：

```json
{
  "batch": 1,
  "games": [
    {
      "name": "羊了个羊：星球",
      "boards": ["wx/人气榜", "wx/畅销榜"],
      "ranks": {"wx/人气榜": 1},
      "category_l1": "休闲", "category_l2": "消除",
      "publisher": "北京简游科技有限公司",
      "first_seen": "2026-06-29", "appearances": 72, "best_rank": 1,
      "profile_value": "high",
      "seed": {"gameplay_desc": "消除", "tags": [], "notes": "", "developer": "..."},
      "media": {
        "matched": true,
        "match_name": "羊了个羊：星球",
        "match_score": 1.0,
        "screenshots": ["https://.../392x696bb.jpg", "..."],
        "icon": "https://.../512x512bb.jpg",
        "description": "官方商店描述全文……",
        "file_size_bytes": 537141248,
        "seller": "Beijing Jianyou Technology Co., Ltd.",
        "version": "1.27.5", "release_date": "2022-09-29",
        "rating": 4.7, "rating_count": 34945,
        "url": "https://apps.apple.com/cn/app/id1644374326"
      }
    }
  ]
}
```

`media` 是**官方一手材料**（App Store），`description` 是官方玩法介绍，
`file_size_bytes` 是安装包体积——**这是判断美术素材量级最硬的代理指标**，务必用上：

| 包体 | 含义 |
| --- | --- |
| < 20 MB | 极轻，素材基本可程序化生成或用通用素材库 |
| 20–80 MB | 轻，少量定制美术即可 |
| 80–250 MB | 中，需要成体系的 UI + 关卡美术 |
| 250–600 MB | 重，大量序列帧/骨骼动画/音效 |
| > 600 MB | 很重，通常伴随大量 3D 资源或长线内容资产 |

## 二、你要做的调研

1. **先读输入里的 media**：官方描述、截图列表、包体、开发商，这些不用再查。
2. **再联网查证**（用 web 搜索 / 抓取官方或商店页面）。优先查：
   - 这款游戏用什么引擎（Cocos Creator / Unity / LayaAir / Egret / 自研 H5）——
     找招聘 JD、开发者访谈、技术分享、引擎官方客户案例，这些比猜测可靠得多；
   - 是 2D 还是 3D（看截图与描述，注意「2D 美术 + 3D 渲染」这种混合情况）；
   - 开发商是谁、是否有同玩法的其他产品（判断这是原创还是换皮矩阵）。
3. **每款至少 1 次检索**。查不到硬信息就据画面与玩法**推断**，但必须把该项标成
   `inferred`，不要伪装成已证实。

> 重要：**不要编造**具体引擎版本、技术细节、公司名。不确定就写推断并降置信度。

### 多地区版本（本次会碰到）

同一个产品常以不同语种名字分别上各区的榜，例如
`Gossip Harbor: Merge & Story`（美区）与 `ゴシップハーバー:マージ & ストーリー`（日区）
是同一款游戏。判断方法：媒体材料里的 `seller`（发行商）与 `release_date` 相同、
截图画风一致。遇到这种情况：

- **仍然按输入里的 name 各产出一份**（站点按榜单名关联，不能合并）；
- 但在 `tech.notes` 里点明「与 xxx 为同一产品的地区版本」，
  并按**同一产品**给分——不要因为是日区就臆造不同的技术栈；
- `sources` 里可以放同一批链接。

## 三、成本维度怎么打分

`tech.dims` 共 8 项，每项 **1–5 的整数**，**1 = 最容易/成本最低，5 = 最难/成本最高**。
不要反过来填。参考锚点：

| 维度 | 1 分 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| `engine` 引擎与框架 | 有现成小游戏模板，改配置即可 | 需在成熟引擎上搭一套自己的框架 | 需自研或大量改造引擎能力 |
| `art` 美术素材量 | 几何图形/纯文字，可程序化生成 | 需要成体系的 UI 与关卡美术 | 海量 3D 资源或长线内容资产（包体 > 600MB 常落这里） |
| `anim` 动画与特效 | 几乎无动画 | 常规 Tween / 序列帧 | 骨骼动画 + 大量粒子/后处理 |
| `physics` 物理与手感 | 无物理 | 简单碰撞/吸附 | 刚体模拟、拖拽手感精调、布料/流体 |
| `logic` 玩法逻辑与关卡 | 单关卡单规则 | 需关卡编辑器 + 数十关设计 | 复杂系统（合成树/战斗/经济）或海量关卡 |
| `data` 数值与养成体系 | 无成长线 | 单线养成 | 多线养成 + 经济循环 + 赛季内容 |
| `server` 服务端与联网 | 纯单机 | 排行榜/云存档 | 实时对战或强联网社交 |
| `audio` 音频 | 无或通用音效 | 定制 BGM + 音效 | 全定制配乐与语音 |

`tech.cost_score` 与 `cost_level` **不用你算**，合并脚本会按 8 维均值自动补齐。
但请给出 `tech.dim_notes`：**每个维度用一句话说明为什么给这个分**，
这是给技术同学看的关键信息（可以只给打分 4–5 与 1 的维度写）。不要写空话。

## 四、玩法/爽点/创新点怎么写

- `play.core_loop`：**一句话到三句话**讲清核心循环（玩家在重复做什么、
  为什么停不下来）。不要罗列系统，要写清「一局是怎么玩的」。
- `play.highlights`（爽点）：**2–5 条**，具体到机制。写「合并同类项时的连锁爆破音效
  与屏幕震动」而不是空泛的「很解压」。要解释**为什么爽**。
- `play.innovations`（创新点）：**1–4 条**。相对同品类做了什么不一样的事。
  **如果确实没有创新，就写「无实质创新，属于成熟品类的执行优化」，不要硬凑。**
- `play.target_user` / `monetization` / `lifecycle`：各一句。
  变现写清类型（IAA 广告 / IAP 内购 / 混合）与广告位设计；
  生命周期写它是**短平快爆款**还是**长线运营**。

## 五、复刻建议怎么写

`clone.verdict` 只能取这 5 个值之一：

| 取值 | 什么时候用 |
| --- | --- |
| `换肤` | 玩法机制照搬就成立，瓶颈在题材/美术。换皮即差异化——成本最低 |
| `变种创意` | 核心机制有可取处，但**必须改一处结构**（换核心循环的一环/换数值模型/换目标人群），照抄会撞车 |
| `微创新` | 整体已成熟，只值得在细节做体验升级；不建议独立立项 |
| `原样复刻` | 纯工具型/无版权与品牌壁垒的玩法原型，适合作为**内部练手或填充位**，不建议当主力 |
| `不建议` | 有 IP/版权风险、依赖独家资源、需重资本投入、或玩法已被头部锁死 |

- `clone.rationale`：2–4 句，讲清**为什么是这个结论**（成本 + 竞争 + 风险）。
- `clone.suggestions`：2–4 条**可执行的差异化动作**。写「把消除题材换成
  『中药抓药台』，用称重/配比替代三消匹配」这种能直接进立项会的建议。
- `clone.risks`：1–3 条，写**真的会出问题的地方**：
  版权/商标、平台审核、素材授权、买量成本、玩法已饱和等。
- `clone.effort`：人日区间，如 `"15–25 人日（1 前端 + 0.5 美术）"`。
  以「一个有成熟小游戏基建的 2–3 人小组」为基准估算。

## 六、结合业务的建议怎么写

`clone` 回答的是「**要不要抄、抄要多少钱**」；`biz` 回答的是另一个问题：
**不管抄不抄**，这款产品的机制、生态位、发行背景，能和我们手里的业务发生什么关系。

它必须同时答好两个视角的问句：**用户为什么要（这套东西在玩家那端成不成立）**，以及
**我们为什么做（为什么是我们、为什么是现在）**。这两句分别对应主体 `why` 的 2 条用户视角
与 2 条业务视角 —— 缺任何一边，这份建议都只是个半成品。

**三层权重差别很大，不要平均用力**：

| 子块 | 权重 | 写法 |
| --- | --- | --- |
| `internal` 内部落地 | **主体** | 按 **424 法则**展开：4 条为什么（**用户视角 2 + 业务视角 2**）/ 2 条怎么做 / 4 条收益 |
| `opportunity` 对外机会 | 附属 | 最多 **2 条**，一句话一条，不做展开论证 |
| `extension` 场景延展 | 附属 | **1–2 个**，每个一句话点到改造点 |

另外两层已明确弱化：写多了会被校验提示压缩，也会把主体淹掉。

> **按通用口径写，不要假设我们具体在运营什么产品。** 写到具体产品时用
> 「若自有产品线含 XX 品类」这类条件句 —— 档案要能给任何一条业务线复用。
>
> **排版**：`why[].text`、`how`、`gain`、`points`、`scene`、`summary` 都是纯文本，
> 页面对它们只解析 `**粗体**` 一种行内标记（用来强调关键判断），
> **其余 markdown（`-` 列表、`` ` `` 代码、`#` 标题）不会被渲染**，写了会原样显示。
> 每条控制在一句话内，写作时就把长度压住 —— 页面按条排布，长句会撑爆版面。
> `why` 是唯一的结构化条目：每条写成 `{"lens": "用户"｜"业务", "text": "..."}`，
> 页面会把视角渲染成标签，读者一眼能分清哪句在说用户、哪句在说我们。

### 1. `biz.internal` — 内部落地（主体，按 424 法则写）

判断这套东西能不能拆出来、挪进已有的产品或运营里。`fit` 只能取三个值：

| 取值 | 什么时候用 |
| --- | --- |
| `可复用` | 有成型模块可整块拿走（排行榜 / 复活 / 每日重置 / 广告节奏），不依赖独家资源，接进来就能跑 |
| `需改造` | 思路可取，但机制与现有产品结构不兼容，必须重构才能用（经济模型、战斗框架） |
| `不建议搬` | 与常规产品线冲突：依赖独家 IP、需要重资本基建、会把产品带偏 |

内部落地分三层，**条数就是权重**：`why` **4 条**、`how` **2 条**、`gain` **4 条**。
这三层是这份档案最该被读的部分，写满、写具体；不要靠形容词凑数。

> **结论为 `不建议搬` 时三层照写，但语义要转过来**（否则会自相矛盾）：
> `why` 的**业务视角**写为什么不能搬（壁垒、成本量级、与产品线冲突），
> **用户视角**写用户被原作锁在哪一环、我们的用户为什么不缺这套（所以没有迁移的必要）；
> `how` 写**如果只取可迁移的那一层该怎么做**，
> `gain` 写**规避掉的投入 + 还能拿走的可迁移方法**。空着不写会被判为没写透。

#### `why`（4 条）— 为什么值得搬：**用户视角 2 条 + 业务视角 2 条**

每条写成 `{"lens": "用户"｜"业务", "text": "一句话"}`，4 条里两个视角**各 2 条**。

这不是格式洁癖。只写业务侧，档案会变成一份「对我们顺手」的建议，却不回答用户买不买单；
只写用户侧，又回答不了这笔投入该不该花。两个视角摆在一起，读的人才能自己下判断。

**① 用户视角 ×2** —— 站在玩家那一边，回答「这套东西在用户端为什么成立」：

| 序 | 答什么 | 写法 |
| --- | --- | --- |
| 1 | **用户动机** | 它打中了用户哪根神经（收集欲 / 掌控感 / 社交比较 / 即时反馈 / 叙事跟随 / 少动脑），必须落到**本作的真实表现**上（在榜时长、评价数与评分、买量素材），不要空谈人性 |
| 2 | **迁移接受度** | 把它搬到我们的产品里，用户买不买账：规则能不能一句话讲清、有没有现成认知、去掉原作哪一环体验会掉 |

- ✅（①用户）「消除反馈密度高到能替代刷短视频的即时满足，本作 72 天在榜、3.4 万条评价 4.7 分，说明这不是靠买量硬撑起来的量」
- ✅（②用户）「规则一句话讲得完（三个一样就消掉），存量用户不需要教学，首日不会因为看不懂而流失」
- ✅（②用户）「原作爽点有相当一部分来自题材梗，换掉题材后老玩家的分享欲会掉，要在素材上补回来」
- ❌（①用户）「符合人性中对收集与成就的追求」（除了人性没给出别的信息）

**② 业务视角 ×2** —— 站回我们自己，回答「为什么是我们、为什么是现在」：

| 序 | 答什么 | 写法 |
| --- | --- | --- |
| 3 | **贴合点 + 杠杆** | 和自有业务的哪块能力对得上（活动位 / 收集线 / 广告位 / 赛季体系…）；改动量 vs 撬动的指标（日活 / 留存 / ARPU / 素材产能），点出性价比 |
| 4 | **时机 / 不做的代价** | 现在能接的原因（已有基建、正在做赛季、买量成本变化、平台政策）；不做的话继续损失什么，或用它的方式能绕开的坑 |

- ✅（③业务）「机制与题材解耦：剥离 IP 与剧情后玩法逻辑仍成立，可整块搬进活动位」
- ✅（③业务）「实现成本极低：纯 2D 点击 + 简单堆叠，无物理无联网，前端一周可出可玩版本」
- ✅（④业务）「不做的话日活只能靠推送硬拉 —— 现在缺的正是一个不需要推送、玩家自己会回来的每日理由」
- ❌ 「玩法很有意思，值得借鉴」

#### `how`（2 条）— 怎么做

**只写 2 条**，这是全节的行动项，必须能直接派活：**做哪个模块 + 动哪一环 + 怎么验证**
（上线灰度 / A/B 对照 / 一周内可验证）。写成一堆 wish list 等于没写。

- ✅ 「搬「每日 0 点重置 + 省队排行」整块做赛季化活动：不动主玩法排期，入口挂一号位，一周内看次日留存」
- ✅ 「把「复活 / 洗牌 / 加槽位」三个激励视频位按它的触发时机与频次 1:1 复刻，跑 A/B 校准自有广告点位」

#### `gain`（4 条）— 会带来什么收益

写**搬完之后具体拿到什么**，不写「提升用户体验」。四条尽量覆盖不同类别：

| 类别 | 例子 |
| --- | --- |
| 可量化的效果 | 次日留存 / 广告渗透率 / 单用户广告次数 |
| 可沉淀的资产 | 抽成组件、活动框架、可复用的排期模板 |
| 省下的成本 | 省掉一轮定价实验、省掉外包课件、不占主玩法排期 |
| 规避的风险 | 明确不做某项高投入、避免团队反复讨论同一件事 |

- ✅ 「一次性道具与激励视频的换算关系可直接当广告位定价标尺，省掉一轮定价实验」
- ❌ 「有助于提升产品竞争力」

### 2. `biz.opportunity` — 对外商业机会（弱化：≤2 条）

`fit` 只能取三个值：

| 取值 | 什么时候用 |
| --- | --- |
| `推荐接触` | 有真实合作空间：正在起量、发行商有代理/联运需求、题材可授权、团队可并购 |
| `可观望` | 有条件成立，取决于具体诉求（价格、区域、版本），值得进观察名单 |
| `不建议接触` | 版权/资本/合作关系已锁死：自家发行、平台独占、IP 方不放权、体量远超我们 |

`points`：**最多 2 条，一句话一条**。只写「**谈什么 + 卡在哪**」，不铺陈发行商背景与行业地位。
第 1 条给结论性事实（谁在自研自发、有没有对外通道），第 2 条给唯一可谈点或明确否定。

- ✅ 「Microfun 自持 Merge Mansion 与本作，是 merge 赛道头部，短期没有放代理的动机」
- ❌ 用三四条写发行商历史、融资情况、赛道地位

### 3. `biz.extension` — 业务场景延展（弱化：1–2 个）

`scenes`：**1–2 个**，每项 `{scene, how}`：

- `scene`：**具体场景名**（「电商大促凑单」「品牌私域签到」「教育机构背单词」），
  不要写「营销场景」这种大类；
- `how`：**一句话**，必须指出**改哪一环**，不要展开整套方案。

- ✅ `{"scene": "电商大促凑单", "how": "把「集齐三个即消除」改成「集齐 N 件同品类解锁满减券」，槽位上限当购物车容量"}`

### 4. `biz.summary`

一句话总括，**30 字内**：把 424 的结论压成一句（值不值得搬 + 主要拿什么），
给不展开看的人用。**不要复述三层目录。**

## 七、输出格式（严格遵守）

写到 `data/detail/_staging/batch_<N>.json`，一个 JSON 数组，**每款一个对象**：

```json
[
  {
    "name": "羊了个羊：星球",
    "updated_at": "2026-09-15",
    "generated_by": "agent",
    "tech": {
      "engine": "Cocos Creator",
      "engine_evidence": "inferred",
      "dimension": "2D",
      "art_style": "扁平卡通，微立绘贴图",
      "dims": {"engine": 2, "art": 3, "anim": 2, "physics": 2,
```

### 硬性要求

- `name` 必须**与输入里的 name 完全一致**（站点靠它关联）。
- `tech.dims` 必须是**全部 8 个键**，值为 1–5 的整数。
- `play.highlights` 至少 1 条；`clone.verdict` 必须是上面 5 个值之一。
- `biz` 三个子块必须齐全：`internal.fit` 取 `可复用/需改造/不建议搬`，
  `opportunity.fit` 取 `推荐接触/可观望/不建议接触`；
  主体 `internal` 必须按 **424** 写齐 —— `why` 4 条、`how` 2 条、`gain` 4 条；
  `why` 的每条是 `{lens, text}`，`lens` 取 `用户` 或 `业务`，**两个视角各 2 条**；
  附属层 `opportunity.points` **≤2 条**、`extension.scenes` **1–2 个**，
  每项都带 `scene` 与 `how`。
- `sources` 至少 1 条真实 URL（可以是输入里给的商店链接）。
- `shots` 留空数组即可——截图由流水线从 `media` 自动注入，你不用管。
- 不要添加规范里没定义的顶层键。
- **不确定的信息进 `evidence` 并标 `inferred`，绝不要当事实写进正文。**
- `biz` 是**判断性内容**，不需要额外检索就能写；但涉及发行商/区域/合作关系的论断，
  必须基于你已查到的信息，不要凭产品名气臆测商务姿态。

### 只回填「结合业务的建议」时

如果任务说明是「只补 `biz`」，输出数组里**每项只放 `name` 和 `biz` 两个键**，
不要重抄 `tech` / `play` / `clone` —— 合并器识别到「有 biz、无 tech/play/clone」
就会把它当补丁打在已有档案上，不会覆盖已定稿的内容。
